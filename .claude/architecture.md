## snapshot.json schema — CONTRACT, do not change silently
Status: **FROZEN as of Session 0 (2026-08-29).** Any later change is a deliberate decision, must be recorded in the session log with a reason, and must happen in the same session as the code change (per CLAUDE.md).

```json
{
  "schema_version": 1,
  "last_updated": "ISO-8601 timestamp",
  "active_window": {
    "app_name": "string",
    "window_title": "string | null",
    "captured_at": "ISO-8601 timestamp"
  },
  "recent_commands": [
    { "command": "string", "ran_at": "ISO-8601 timestamp" }
  ],
  "voice_note": {
    "transcript": "string | null",
    "summary": "string | null",
    "recorded_at": "ISO-8601 timestamp | null"
  },
  "browser_tab": {
    "url": "string | null",
    "title": "string | null",
    "captured_at": "ISO-8601 timestamp | null"
  }
}
```

Decisions (Session 0):
- **`schema_version`** — new field, starts at `1`. Reason: gives readers a cheap way to detect a future schema change instead of guessing from field presence.
- **`recent_commands` cap** — keep the last 20, FIFO drop-oldest when appending. Reason: bounds file size without needing a separate pruning pass.
- **Write coordination** — NOT "each component writes its own key independently" as originally proposed. All backend components run inside the same Tauri/Rust process, so writes go through a single in-process `Mutex<Snapshot>` guarding the whole struct; the holder of the lock serializes the full struct and writes it atomically (write to a temp file on the same volume, then rename over `/mnt/c/...snapshot.json`). Reason: independent per-key read-modify-write from multiple components is a race — one component's write can silently clobber another's key even if each "owns" a different key, since a write serializes the entire file. A single mutex + atomic rename makes last-write-wins actually true and needs no cross-process file lock.
- **Missing/not-yet-populated source** — always include the key; use `null` for scalar/object fields (e.g. `voice_note.transcript` before any recording) and `[]` for `recent_commands` before any command is logged. Never omit a top-level or nested key. Reason: one shape for every reader (Rust serde structs, TS interfaces, resume card UI) — no separate "key missing" vs "key null" branches.
- **`last_updated`** — set by the shared writer on every write, regardless of which key changed. Reason: with multiple components touching the file, this must mean "most recent write to anything," not "most recent write to a specific section."

Decisions (Session 1):
- **`active_window` as a whole may be `null`.** Clarification of Session 0's null rule, **not** a version bump — `schema_version` stays `1`. Reason: the frozen block types the inner fields as non-nullable (`app_name`, `captured_at` have no `| null`, unlike every field of `browser_tab`), which left no legal value for "nothing captured yet" — and the shared writer must create the file before any capture has succeeded. Reading "use `null` for scalar/object fields" as covering the object as a whole resolves it without touching the inner types. Consequence for readers: `active_window` is either `null` or **fully** populated — it is never half-filled with placeholder strings, so there is no sentinel like `app_name: ""` to check. TS readers need `ActiveWindow | null`.

## Known limitations
- **whisper hallucinates on near-silent input.** Digitally-pure silence transcribed as `"you"`. Realistic faint room noise correctly yields `[BLANK_AUDIO]`, which `clean_transcript` filters to `""`, so the common case is handled — but a short spurious word can still reach `voice_note.transcript` from a quiet recording. Not filterable by heuristic without also dropping genuine one-word notes.
- **Transcription accuracy is `base.en` accuracy.** Clean input is near-perfect (a TTS WAV round-tripped word-for-word); acoustic pickup with background audio degrades noticeably. If it disappoints in real use, the fix is `small.en` (~460 MB) via `HUMCON_WHISPER_MODEL` — no code change.
- **The whisper binary and model are an unversioned manual install** outside the build (see the setup note above). A fresh machine gets a startup warning and no transcription until they are placed. The release is DLL-dependent: `whisper-cli.exe` without its `whisper.dll`/`ggml*.dll` siblings will not launch.
- **A denied microphone is handled but never runtime-tested.** `classify_stream_error` detects it by message text because cpal 0.18 maps `E_ACCESSDENIED` to the generic `BackendError`; if cpal ever changes that wording the specific hint silently degrades to a generic message. The `ErrorKind::PermissionDenied` arm is kept for that eventuality.
- **The hotkey is hardcoded to `Ctrl+Alt+Space`** with no config or rebinding. If another app already owns the combo, registration fails, one error line is logged, and voice notes are simply unavailable for that run — the app still starts.
- **`last-recording.wav` is overwritten every recording** and never cleaned up. It is scratch space, not history, but it does mean the most recent voice note sits on disk as audio indefinitely — worth knowing before pointing this at anything sensitive.
- **Only one recording at a time, by construction.** Pressing the hotkey during transcription starts a *new* recording rather than queueing: the state returns to idle the instant the stop press is handled, so the app can never wedge, but a second note started quickly can have its `voice_note.transcript` overwritten by the first one's slower whisper run finishing after it.
- **Volatile titles churn the file.** We write on every *successful* poll (so `captured_at` means "we looked and saw this then", making a stale timestamp unambiguously "capture is failing or stopped"). The cost: apps whose title animates — Windows Terminal running Claude Code cycles `◐ ◑ ✳` in its title — rewrite snapshot.json every 3s indefinitely. Switching to write-on-change would not fix this case, because the title genuinely is changing. If churn becomes a problem, the fix is a title-normalising filter, not a change to write cadence.
- **`SearchHost` displaces the real app.** Pressing Start puts the Windows search UI in the foreground and it is recorded as the active app (`app_name: "SearchHost"`), overwriting whatever you were actually working in. This is arguably the same category as the desktop window we already filter. **TODO / product call:** decide whether the filter should widen to a small set of shell surfaces (SearchHost, Task View, "Task Switching" — all observed in Session 1 testing) rather than just Program Manager. Not changed unilaterally because it defines what "the app you were in" means.
- **Window titles are truncated at 254 UTF-16 code units** by a fixed buffer inside `active-win-pos-rs`, with no retry. Verified from the crate's source, not at runtime. An emoji costs 2 units, and a cut landing mid-surrogate-pair yields a trailing U+FFFD.
- **`app_name` is a display name, not a stable key.** It is the executable's `FileDescription` version resource, so it is localized and changes with app version; it also produces oddities like `WhatsApp.Root`. Falls back to the exe stem when the resource is missing. Use `process_path` if a stable identifier is ever needed — the schema does not currently carry one.
- **`Err(())` is opaque.** No-focus, lock screen, and protected processes (antivirus UIs, SYSTEM-owned windows) are indistinguishable. Do not use this crate's `Err` to infer that the screen is locked.
- **Lock-screen behaviour is inferred, not verified** (see Session 1 log).
- **The `windows` crate now compiles at three major versions** — 0.48 for `active-win-pos-rs`, 0.61 for Tauri, 0.62 pulled in by `cpal`/`global-hotkey` (Session 4). It links and works; cost is build time and binary size only. If `active-win-pos-rs` ever needs replacing, the direct `windows-rs` equivalent is ~50-70 lines.
- **`snapshot.json` is not yet bounded in write frequency** and has no reader-side change notification. ~~The resume card UI will need to poll it or watch the file~~ — **stale as of Session 5**: it does poll (`src/main.ts`, 1s interval plus on focus/visibility change). Left here, struck through rather than deleted, so this doesn't get re-flagged as an open question by a future session skimming this list.
- **Only interactive WSL commands are captured.** `PROMPT_COMMAND` fires nowhere else, so commands run by non-interactive tooling — including Claude Code's own Bash tool — never reach the log. This is deliberate: those would flood `recent_commands` and are not what "what was I doing" means. It does mean the log reflects hand-typed work only.
- **The secret filter over-matches on purpose.** Any command matching `password|passwd|secret|token|api[_-]?key|bearer|credential|private[_-]?key|ssh-add|gpg|…` is skipped entirely rather than redacted, per the project constraint. So `man passwd` silently never appears. That tradeoff is intentional — a dropped command costs nothing, a leaked secret cannot be un-leaked — but it means the log is not a complete history.
- **Requires bash history to be enabled.** The hook reads `history 1`; with `HISTSIZE=0` or `set +o history` it silently logs nothing.
- **Multi-line commands are flattened** — embedded newlines and tabs become single spaces so each log entry stays one JSON line.
- **The frozen schema carries no exit code and no working directory** for a command, only `command` and `ran_at`. A failed command is indistinguishable from a successful one. Adding either is a schema change and must follow the CLAUDE.md rule.
- **The raw `commands.jsonl` is trimmed** to its last 100 lines once it passes ~64 KB. Only the last 20 ever reach the snapshot, so this loses nothing that matters, but it is not an audit log.
- **Two writers now share the snapshot mutex**, each polling on its own thread (window capture 3s, command log 2s). Contention is negligible today, but adding more pollers means adding more whole-file rewrites — prefer change-detection over unconditional writes in any new component.
- **WSL environment variables do not reach Windows processes.** `FOO=bar cargo.exe run` leaves `FOO` unset on the Windows side; only variables named in `WSLENV` cross over (`WSLENV=FOO FOO=bar cargo.exe run`). This fails *silently* — the override is ignored and the run looks successful, which reads as a code bug. Affects every `HUMCON_*` override and `ANTHROPIC_API_KEY` (see the Session 4 log).
- **Never use file metadata for change detection across the WSL/Windows boundary.** `fs::metadata`'s size and mtime can be stale for a file WSL is appending to, which produces a silent stall rather than an error (see the Session 2 log). Read and compare content instead.
- **The browser endpoint's only defense is a header, not a secret.** `X-HumCon-Extension` stops a hostile web page (no CORS route can add it and still get a response — see Session 6) but does nothing against another **local process**, which can send the same header. Accepted for a first pass: the impact is a wrong `browser_tab` in a local file, not a leak. Revisit with a shared token (generated at startup, read by the extension via an options page) if that gap ever matters.
- **The browser server is single-threaded**, like every other producer in this codebase — `server.incoming_requests()` is handled one at a time on its own thread. A client holding a connection open would stall the next request. Acceptable for a loopback endpoint talking to one well-behaved extension; would need worker threads if that assumption ever changes.
- **Three producers now share the snapshot mutex** (window capture 3s, command log 2s, browser server on-event). The Session 2 note about preferring change-detection over unconditional writes applied directly here: see the Session 6 log entry for a bug where change-detection was implemented but had no effect until the check was moved outside `SnapshotStore::update`, which stamps `last_updated` and writes unconditionally once called regardless of what its closure does.
- **`HUMCON_PORT` is not the only place the port lives.** `extension/manifest.json`'s `host_permissions` and `background.js`'s `ENDPOINT` both hardcode `7423`. Overriding the Rust side via `HUMCON_PORT` without editing both of those breaks the extension silently — it will simply never reach the server (and CORS will block it from even discovering why).
- **Chrome/Brave's DevTools HTTP API requires `PUT` for `/json/new`**, not `GET` as older documentation and examples show — this Chromium version (152.x) returns `405` on `GET`. Only relevant to whoever next automates browser testing this way; the shipped extension doesn't use this API at all, it's a testing tool.
